# Daily inventory setup

1. Review and run `inventory-schema.sql` once in the Supabase SQL editor for the existing project. This migration creates only new inventory tables, RLS policies and a function; it is **not** executed automatically. Back up your database first. Rollback, if required: drop function `public.inventory_save_import(date,text,jsonb,text)`, then drop tables `inventory_imports`, `inventory_mappings`, `inventory_entries`, `inventory_items` in that order (this deletes inventory data).
2. Serve the site as usual over HTTPS (or localhost for development), sign in, and open `inventory.html`. The captain will integrate navigation and service worker caching separately. Schema and user session are required.
3. Add stock items with a start date and initial count. For each date, save purchase and damage separately per item. Sale comes from a POS report. Closing is opening + purchase − sale − damage; gaps carry the last balance forward. Counts before an item's start date are not available. A negative closing is shown as a shortage, not blocked. Editing an initial count, an earlier movement or an earlier imported sale recalculates all later openings on the next read; no derived balances are persisted. Start dates cannot be edited after creation.
4. Upload an `.xls` or `.xlsx` report locally. The **first sheet** must have a single unambiguous date before a `Category / Item / Code / Qty. / Total` header, using DD/MM/YYYY or YYYY-MM-DD (also accepts dots and hyphens). Ranges with different dates are rejected. Category-only rows and total/subtotal rows are excluded. Item rows must have a non-negative numeric quantity. The importer uses quantity as plates and a bracketed count such as `[3 Pieces]` or `(1 Piece)` as pieces per plate, defaulting to one, including thali. Check the displayed dishes and totals carefully against the original report before confirming. Other report layouts or date formats may need conversion first; unsupported layouts are rejected rather than guessed.
5. Choose an item or **Ignore** for every distinct category + item name + code. Names and categories distinguish reused codes; no automatic matching is performed. Multiple dishes may map to one item. Choices are saved per user on confirmation and can be edited on the next report. Past imports are snapshots, so changing a mapping does not rewrite past sales; reimport that day to replace them. Mapping preferences may save even if the subsequent import fails; errors are displayed.
6. The report date must match the selected date. The preview shows totals and warns before replacing an existing day's entire import. The same normalized report and choices are detected as a duplicate. A changed report or mapping requires explicit replacement. Concurrent changes to the day's import cause an error instead of silently overwriting another user's tab; preview again. A replacement can contain zero sales when every dish is ignored.

## Privacy and limitations

The browser loads the pinned SheetJS Community Edition reader `xlsx@0.18.5` from jsDelivr (https://cdn.jsdelivr.net/npm/xlsx@0.18.5/dist/xlsx.full.min.js); it parses the chosen file locally. The raw workbook is not uploaded, though mapped aggregate sales and mapping choices are saved to Supabase. Do not use sensitive or untrusted workbooks: this older community release has known security issues, and the CDN must be reachable. Files are limited to 10 MB. The existing Supabase JS library and site assets also require their configured networks. Web Crypto (HTTPS or localhost) is needed for duplicate fingerprints. Data is read from Supabase on page load and after saves; offline use and continuous cross-tab updates are not supported. Refresh before making decisions if another device is editing stock. Import replacement is atomic and checks for concurrent replacement; ordinary item and movement edits are last-write-wins. Browser arithmetic uses JavaScript numbers; display is rounded to four decimal places, while stored movements retain entered precision. No real sales data or credentials are included.

Run the focused checks with `python3 -m pytest -q tests/test_inventory.py` (Node.js required). These test synthetic rows and pure logic, not the live Supabase policies or third-party spreadsheet parser.
