# Daily inventory setup

1. Review and run the SQL migrations manually in order in the Supabase SQL editor for the existing project (they are **not** executed automatically by the app; back up your database first):
   - First: `inventory-schema.sql` (creates `inventory_items`, `inventory_entries`, `inventory_mappings`, `inventory_imports`, base RLS policies, and `public.inventory_save_import`).
   - Second: `inventory-safe-clear.sql` (additive migration creating `public.inventory_corrections` with owner-only `SELECT` RLS, replacing `inventory_entries_owner` with `inventory_entries_read` so movement writes go through locked RPCs, and creating `public.inventory_save_entry`, `public.inventory_clear_day`, and `public.inventory_restore_correction`).
   - Rollback, if required: drop functions `public.inventory_restore_correction(uuid)`, `public.inventory_clear_day(date,text,text,jsonb,text)`, `public.inventory_save_entry(uuid,date,numeric,numeric,boolean,numeric,numeric)`, `public.inventory_save_import(date,text,jsonb,text)`, then drop tables `inventory_corrections`, `inventory_imports`, `inventory_mappings`, `inventory_entries`, `inventory_items` in that order (this deletes inventory data).
2. Serve the site as usual over HTTPS (or localhost for development), sign in, and open `inventory.html`. The captain will integrate navigation and service worker caching separately. Schema and user session are required.
3. Add stock items with a start date and initial count. For each date, edit Purchase and Damage inline (calculated Closing updates live; keyboard: **Enter** moves Purchase → Damage → Save, **↑ / ↓** moves between active rows) and save per row. Sale comes from a POS report. Closing is opening + purchase − sale − damage; gaps carry the last balance forward. Counts before an item's start date are not available. A negative closing is shown as a shortage, not blocked. Editing an initial count, an earlier movement or an earlier imported sale recalculates all later openings on the next read; no derived balances are persisted. Start dates cannot be edited after creation. Stock item deletion, archiving, and hiding are **not** implemented.
4. **Unsaved draft protection across reload:** Unsaved Purchase/Damage row edits, selected stock date, and pending Stock items form inputs are saved in browser `localStorage` scoped per authenticated user (`inventory_drafts_v1:<user_id>`), separated by date and item, and restored automatically on refresh without writing to Supabase until explicitly saved. Switching dates or re-rendering preserves dirty entries on all dates. A draft status banner shows restored/unsaved counts and provides per-row **Discard** and global **Discard all drafts** controls. Drafts use per-edit revisions and are cleared only after the exact saved revision succeeds (so new edits made while a save is in flight are preserved rather than wiped) or on explicit discard; failed reads or writes keep drafts intact. Stock row saves call `inventory_save_entry` with expected baseline existence/purchase/damage values under the server per-day advisory lock so concurrent clear/restore/save calls cannot silently overwrite newer cloud values; item edits perform a fresh client pre-read check and ask before overwriting changed values. Browser storage errors are shown in a visible alert banner. Credentials, auth tokens, and local Excel workbook contents/unconfirmed import previews are **never** stored in `localStorage` (reselect the local Excel file and review matches again if you reload before confirming import).
5. Upload an `.xls` or `.xlsx` report locally. The **first sheet** must have a single unambiguous date before a `Category / Item / Code / Qty. / Total` header, using DD/MM/YYYY or YYYY-MM-DD (also accepts dots and hyphens). Ranges with different dates are rejected. Category-only rows and total/subtotal rows are excluded. Item rows must have a non-negative numeric quantity. The importer uses quantity as plates and a bracketed count such as `[3 Pieces]` or `(1 Piece)` as pieces per plate, defaulting to one, including thali. Check the displayed dishes and totals carefully against the original report before confirming. Other report layouts or date formats may need conversion first; unsupported layouts are rejected rather than guessed.
6. Choose an item or **Ignore** for every distinct category + item name + code. Names and categories distinguish reused codes. Existing saved mappings and **Ignore** choices always take precedence and remain editable. For unmapped dishes, the importer suggests a stock item only when normalized whole-word matching on the dish item name (accounting for case, punctuation, whitespace, and piece annotations such as `[3 Pieces]`, while avoiding substring false positives) identifies exactly one candidate; suggestions show the matched item and reason and must be explicitly reviewed/accepted before previewing or importing. Ambiguous multi-candidate matches are never auto-mapped and list candidates for manual selection. Multiple dishes may map to one item. Choices are saved per user on confirmation and can be edited on the next report. Past imports are snapshots, so changing a mapping does not rewrite past sales; reimport that day to replace them. Mapping preferences may save even if the subsequent import fails; errors are displayed.
7. The report date must match the selected date. The preview shows totals and warns before replacing an existing day's entire import. The same normalized report and choices are detected as a duplicate. A changed report or mapping requires explicit replacement. Concurrent changes to the day's import cause an error instead of silently overwriting another user's tab; preview again. A replacement can contain zero sales when every dish is ignored.
8. **A4 Print and PNG Export / Share:** Use **Print A4** for a paginated A4 print view or **Share / Export A4 PNG** to generate A4-proportioned PNG page(s) (`1240×1754`) locally in the browser using HTML5 Canvas (no third-party upload). Both include the restaurant name (`profiles.restaurant_name`, fallback `RestroManager`), selected date, all visible stock rows, and the read-only columns `Item, Opening, Purchase, Sale, Closing, Damage` (no form controls). PNG export measures wrapped item-name pixel heights against available vertical A4 canvas space (`ctx.measureText`), paginates cleanly across multiple A4 pages, and splits exceptionally tall rows across continuation slices rather than clipping or omitting text. If the current date has unsaved draft values, explicit confirmation is required and draft values are visibly labeled as **DRAFT**. Print and export never mutate saved Supabase data or clear drafts.
9. **Recoverable day corrections & undo:** In **Day corrections & recovery**, two scoped actions target only the selected date:
   - **Remove imported sales only** (`sales_only`): removes only that day's `inventory_imports` row; that day's purchase/damage rows, initial openings, stock items, saved dish mappings, and other dates remain untouched.
   - **Clear whole day movements & sales** (`whole_day`): clears only that day's `inventory_entries` (purchase/damage) and `inventory_imports`; initial openings, stock items, saved dish mappings, and other dates remain untouched.
   - Before deleting, a confirmation panel displays the target date, exact counts to be removed, untouched items/dates, and later-day recalculation impact. Empty-day actions are safe no-ops. If unsaved local drafts exist on the affected date, clearing or restoring is blocked until you explicitly save or discard those drafts (drafts are never silently deleted or reapplied).
   - Every clear transactionally stores a permanent snapshot in `public.inventory_corrections` (with `SELECT`-only owner RLS; snapshots never auto-expire or purge) and passes a `client_request_id` for idempotent retry safety. Both scopes remain recoverable via **Undo / Restore** even after refreshing the page. Restoring validates all target slots under the same server `(user_id, day)` advisory lock: if any target slot is already occupied (or a referenced item starts later than the snapshot date), restore stops all-or-nothing without overwriting existing rows and keeps the snapshot available until conflicts are resolved.

## Privacy and limitations

The browser loads the vendored, pinned SheetJS Community Edition `0.20.3` reader from `js/vendor/xlsx.full.min.js` (Apache-2.0) to parse `.xls` and `.xlsx` files locally in the browser; raw workbooks are never sent to any server, though mapped aggregate sales and mapping choices are saved to Supabase. Decorative UI icons load from the local SVG sprite `assets/inventory-icons.svg` (no scripts, external resources, embedded images, or fonts).

- **Dependency origin and integrity verification:** Official SheetJS CE `0.20.3` standalone browser build (`https://cdn.sheetjs.com/xlsx-0.20.3/package/dist/xlsx.full.min.js`, upstream tag `v0.20.3` / commit `8a7cfd47bde8258c0d91df6a737bf0136699cdf8` at `https://git.sheetjs.com/sheetjs/sheetjs/tags.rss`, released `2024-07-18`). `0.20.3` resolves the published `0.18.5` CVEs (`CVE-2023-30533` fixed in `0.19.3`, `CVE-2024-22363` fixed in `0.20.2`) and remains the latest official SheetJS CE release listed at `https://cdn.sheetjs.com/` and `https://sheetjs.com/`. Checksums for the vendored `951,904`-byte file:
  - Official SheetJS MD5 (published at `https://docs.sheetjs.com/docs/miscellany/contributing/`): `6b3130af1ceadf07caa0ec08af7addff`
  - SHA-256: `cc015130aa8521e7f088f88898eba949ccdcbfb38df0bd129b44b7273c3a6f41`
  - Upstream source tarball (`xlsx-0.20.3.tgz`) SHA-512 SRI: `sha512-oLDq3jw7AcLqKWH2AhCpVTZl8mf6X2YReP+Neh0SJUzV/BdZYjth94tG5toiMB1PPrYtxOCfaoUCkvtuH+3AJA==`
  - In the build sandbox (where shell egress is limited to GitHub/npm/PyPI), package metadata, license, changelog, and bundle boundary snippets were checked directly against `cdn.sheetjs.com` and `docs.sheetjs.com`, and identical bytes (`MD5 6b3130af1ceadf07caa0ec08af7addff`, `SHA-256 cc015130...`) were cross-verified across independent mirrors before vendoring. Maintainers with unrestricted egress can verify directly via `curl -sSL https://cdn.sheetjs.com/xlsx-0.20.3/package/dist/xlsx.full.min.js | sha256sum`.
- **Browser print & share limitations:** Native Web Share with image files (`navigator.share({ files })` / `navigator.canShare({ files })`) requires a supporting mobile or desktop browser over HTTPS (or localhost) and may disallow multi-file shares or be dismissed by the user; when unsupported, denied, or dismissed, accessible per-page PNG download links appear automatically below the table (some browsers block multiple simultaneous programmatic downloads, so manual per-page links are kept available). Browser printing (`window.print()`) relies on the OS/browser print dialog for paper size/background colors and may be unavailable in some embedded mobile WebViews; use **Share / Export A4 PNG** when printing is unavailable.
- **Operational limits:** Only import trusted POS report workbooks (`0.20.3` has had no newer upstream CE release since `2024-07-18`, and files are capped at 10 MB client-side). Browser draft persistence depends on `localStorage` availability and quota (private-mode restrictions or quota errors trigger a visible warning and keep edits in memory only). The existing Supabase JS library and site assets also require their configured networks. Web Crypto (HTTPS or localhost) is needed for duplicate fingerprints. Data is read from Supabase on page load and after saves; offline use and continuous cross-tab updates are not supported. Refresh before making decisions if another device is editing stock. All per-day stock writers (`inventory_save_import`, `inventory_save_entry`, `inventory_clear_day`, and `inventory_restore_correction`) serialize per `(user_id, day)` using Postgres `pg_advisory_xact_lock(hashtextextended(uid::text || ':' || p_day::text, 0))` with compare-and-swap checks so concurrent tabs cannot half-clear, duplicate restores, or silently overwrite newer server rows; item-level metadata edits (`inventory_items`) continue to perform a fresh client-side pre-read conflict check before updating (a brief race window remains between pre-read and update on item metadata). Browser arithmetic uses JavaScript numbers; display is rounded to four decimal places, while stored movements retain entered precision. No real sales data or credentials are included. Stock item deletion/archiving is not implemented.

Run the focused checks with `python3 -m pytest -q tests` (Node.js required). These test synthetic rows, pure logic, draft storage separation/restoration, mocked RPC CAS/conflict/in-flight revision handling, day-correction confirmation/recovery/draft-blocker flows, SQL migration/permission structure checks, pixel-measured A4 pagination, SVG icon validation, and the vendored SheetJS `0.20.3` reader on synthetic `.xls`/`.xlsx` fixtures — not live Postgres/Supabase RLS/RPC execution or real browser print/canvas rendering.
